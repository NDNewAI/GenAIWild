From Cowork to Code: An Introduction and Practice

You have already used Claude Code once: Step 1 of the research database had you install Obsidian from the Code tab. This page explains what changes when you move from Cowork to Code, then walks you through up to an hour of practice, so that you can take on any recipe on the recipes page.

The shift

In Week 6, Prof. Smiley drew the line between the two tabs this way. In Cowork, you hand Claude a task and a folder, and it works through the steps and hands back finished files. In Code, you work alongside Claude inside a folder: it reads and edits the files there, follows the folder's CLAUDE.md, and learns your skills. His slide also said "No coding required," and that is still true. You will not write code here. You will read what Claude proposes, approve or refuse it, open what it made, and tell it what to fix.

The practical difference is visibility. In Cowork you mostly see the finished result. In Code you see each step as it happens: every file Claude reads, every file it writes and every command it runs, all inside a folder you can open yourself. Code takes more watching because of that, and it is also why Code is the better place to learn how these systems behave.

Prof. Smiley's line from Week 6 is the right attitude for this work: "You aren't prompting, you are… managing." Managing means saying what done looks like, checking the plan, and checking the result.

Ideas that make Code make sense

  1. The folder is the project. Everything Claude makes is an ordinary file in one folder, and you can open any of those files yourself. This is the course's first computing idea, that files live in directories, put to work.
  2. Plan mode is your game plan. Start every new piece of work in Plan mode. Claude lays out what it intends to do before it touches anything, and you read the plan, change it and approve it. Reading a plan for a minute costs less, in time and in usage, than undoing a build you did not want. If Claude heads somewhere you did not expect once it is working, you can stop it and redirect it.
  3. Claude types the commands, and you read them. When Claude asks to run something like python3 build_map.py, it is asking to start a program. Allow it when you understand the explanation and the command stays inside your folder. Deny it when it reaches outside your folder, deletes things you did not ask to delete, or you cannot tell what it does. Then ask Claude to explain.
  4. When you do not understand the question, say so. Claude will sometimes ask you to choose between options that use words you have not met, such as a library, a file format or a "server." Do not pick one just to keep things moving. Answer with something like: "I don't understand the question. Explain each option in plain language, tell me what would happen with each, and tell me which you recommend and why." Then decide. You can also open a separate Claude chat in your browser at claude.ai and ask it there. That keeps your Code session focused on the build, and a short side conversation is a cheap way to learn a term. Keep in mind that the side chat cannot see your folder or your Code session, so paste in the exact question or option you are asking about. Often it is easier to take a screenshot of what Claude is asking and drop it into the chat, because the screenshot shows the buttons and context too. On a Mac, press Command + Shift + 4 and drag over the area. On Windows, press Windows + Shift + S. Never paste in a key from a .env file, and check that a screenshot doesn't show one. Use its answer to help you understand the choice, and then make the decision yourself. It's normal not to know these terms. Just don't approve anything until you do.
  5. The work happens in a loop. Claude builds, you open the result and look, you tell Claude what is wrong, and it fixes it. Expect three or four turns of this loop before something looks right.
  6. Error messages tell you what went wrong. A red message is the computer reporting what failed. Paste it back to Claude, or just say "it failed, read the error." Nobody gets through a build without errors.
  7. What Claude knows about your project is in the files. Prof. Smiley called CLAUDE.md the "brain" of the folder. It is really a plain text file of rules, and it works because Claude reads it at the start of every session. A short notes file does the same thing for where you left off. Starting a fresh session with a good notes file is also the cheapest way to keep working when you are close to your usage limit.
  8. You can undo. Claude Code saves checkpoints as it works, and you can rewind to one. Before any big change, you can also copy the whole folder and name the copy with the date.

Your resources are finite and time-based

Your plan gives you a limited amount of Claude use, measured in time windows. One limit resets every five hours, and a second limit covers the whole week. Chat, Cowork and Code all count against the same limits. Work that is spread over several days therefore gets far more done than the same work crammed into one night. Three habits from Prof. Smiley's Week 6 slides keep you from getting stuck the night before a deadline.

HaikuQuick and light. Sorting, tagging, short questions.
SonnetYour default for the practice below and for most projects.
OpusFor hard, multi-step work across many files. Use it when a task really needs it.
FableDo not use it on our plan. It uses up your limits very quickly.

First, type /usage before you start something big, to see how much you have left. Second, switch models with /model. Third, when a conversation gets long, write a notes file and start a fresh session instead of pushing on.

On to some practice

Now put those ideas to work. The practice below has eight steps, in the same format as the research database steps from Week 7. Each step says who does it and where. Text in a shaded box is a goal to tell Claude. Use your own words if you like, and fill in anything in [BRACKETS]. Plan on up to an hour, and do it in one sitting if you can.

Step 1. Make a folder to practice in

You · Finder or File Explorer

Pick the path that matches where your research database is today. Everyone ends this step with a folder called GAIW Code Practice in Documents.

Path A. Your database works

Copy the whole GAIW Research Database folder and name the copy GAIW Code Practice. You will practice on the copy, so your real database keeps running untouched.

Path B. You have the folder, but it is not updating or something is broken

Copy it the same way. Step 4 below is where Claude Code helps you find out what went wrong. When you fix the original later, use what you learn on the copy.

Path C. You never got a database folder

Make an empty folder called GAIW Code Practice. Put copies of your own State of the Field files in it: your proposal, your video script, and any notes. Claude will build from those in Step 3.

You're done when

GAIW Code Practice exists in Documents, and nothing in your original database has changed.

Step 2. Open the folder in Code and set it up

You · Claude desktop app, Code tab

Open the Claude desktop app and switch to the Code tab. Start a new session and choose GAIW Code Practice as its folder. Claude can now read and write in that folder and nowhere else. Set the permission mode to Plan. Then type these three commands, one at a time: /status (which account and model you are on), /usage (how much of your usage limits you have left), and /model (pick Sonnet).

You're done when

The session shows your practice folder, the mode says Plan, and the model is Sonnet.

Step 3. Take a tour without changing anything

Claude · Code tab

My goal: understand what's in this folder before we change anything. Walk me through it. Tell me what each folder and file is for, what CLAUDE.md tells you to do, and whether there are any hidden files or folders, like .claude. Assume I've never looked inside a project folder before. Don't change anything.

Path CUse this goal instead: My goal: turn the State of the Field files in this folder into a small research database like the one we built in Week 7. Put my originals in raw/, make a note for each source and each idea, and add an index, a log and a CLAUDE.md with the rules. I write in insights/. You never do. Don't ever violate this rule. Only use sources that are in my files, and never make one up. Show me the plan and wait for my OK.

What you'll seeClaude reads the files and then describes the folder. On Path C, Claude shows you a plan and waits. Approve it when you agree with it, and Claude will ask permission as it creates each file.

To see hidden files yourself, press Command + Shift + . in a Mac Finder window, or choose View → Show → Hidden items in Windows File Explorer.

You're done when

You could explain to a classmate what three of the folders are for.

Step 4. Give the folder a check-up

Claude · Code tab

My goal: find out whether this database is healthy. Check for broken links, notes that nothing links to, sources that are missing key details, and notes the index leaves out. If there's a check-up script in system/, run it. If there isn't one, write one. Then read log.md and tell me whether the scheduled update has run every weekday. If it hasn't, tell me what the log says went wrong. Show me your plan first, and don't fix anything until I say so.

What you'll seeA plan, then a request to run a command such as python3 system/checkup.py. This is your first real permission decision. Read Claude's explanation, check that the command stays inside your folder, and choose Allow.

Path BThis step is where you find out why your database stopped. Common causes are a laptop that was asleep at the scheduled time, a task that was never saved, or a rule in CLAUDE.md that Claude could not follow. Write down what you find.

You're done when

Claude has given you a report with exact counts, and you know what is and is not working.

Step 5. Build something new: a 3D map of your database

Claude, then you · Code tab, then your browser

My goal: a 3D map of this database that I can fly through in my browser. Make each note a dot. Size the dots by how many links they have, and color them by folder (sources, concepts, insights and system). When I click a dot, show me the note's title and its first few lines. Put it all in one HTML file in a new folder called views-3d, and tell me exactly how to open it. Show me the plan first.

What you'll seeA plan, then permission requests to read your notes and write a script and a page. Claude may ask to start a "local server" so your browser can load the page. That is a small program that runs only on your laptop. Allow it, and Claude will give you an address that starts with http://localhost to open.

Then youOpen the page, fly around, and find your own insight notes. Write down one thing that looks wrong.

You're done when

The map opens in your browser and you can click a dot and read a note.

Step 6. Run the loop, and try an undo

You → Claude · Code tab

Tell Claude the thing that looked wrong in Step 5, in plain words, and let it fix it. Then ask for one change you might not want, such as "make every dot the same color." Look at the result. Now undo it. Rewind to the checkpoint before that change, or ask Claude how to do that in your version of the app.

You're done when

You have fixed one real problem and undone one change on purpose.

Step 7. Leave a note for next time

Claude, then you · Code tab

My goal: be able to pick this up tomorrow in a new session. Write a short NOTES.md in this folder that says what we built today, how to rebuild the 3D map, what's still broken, and what I want to try next. Then add a line to CLAUDE.md that tells future sessions to read NOTES.md first. Show me both changes before you save them.

Then youType /usage again and compare with Step 2. That difference is what this practice cost against your limits. Close the session, start a new one in the same folder, and ask "Where did we leave off?"

You're done when

A brand-new session can tell you where you left off without you explaining.

Step 8 (optional). Bring something over from Cowork

You, then Claude · Cowork, then Code tab

Take something you already made in Cowork, such as a page, a document or a spreadsheet. Save or download it into your practice folder. Then ask Claude Code to add one feature to it. This shows you that work can move back and forth between the two tabs.

You're done when

Something that started in Cowork has a new feature added in Code.

Ready to build something of your own? Go back to the recipes and pick one. Make a new folder for it, start in Plan mode, and bring the habits from this practice: check /usage, use Sonnet by default, and keep a NOTES.md.

When you get stuck

The page opens blank

Browsers block some pages opened straight from a folder. Ask Claude to "serve this folder locally and give me the address," then open the localhost address it gives you.

Claude asks to run something you don't understand

Choose Deny, then ask "What does that command do, and does it touch anything outside this folder?" Allow it only once the answer makes sense.

"Command not found"

A program Claude expected is not installed. Ask it to find a way that needs nothing new installed. Claude can usually do the same work with tools already on your laptop.

You hit a usage limit

Claude Code wraps up the current step. Ask it to update NOTES.md if it can, then come back after the reset with a fresh session. Write down when it happened, so you can plan around the limit next time.

You don't understand Claude's question

Say so. Ask Claude to explain each option in plain language, what would happen with each, and which it recommends and why. You can also paste the question, or a screenshot of it, into a separate claude.ai chat in your browser, ask a classmate, or bring it to office hours before you answer.

Claude changed the wrong file

Rewind to the checkpoint before the change. Then add a rule to CLAUDE.md that names the files it should leave alone.

The conversation feels lost

Long sessions drift, and they also count more heavily against your usage limits. Ask Claude to update NOTES.md, start a fresh session, and say "read NOTES.md and continue."

Words to know

folder (directory)
A container for files. In Code, the folder you choose is the only place Claude can read and write.
path
The address of a file, such as Documents/GAIW Code Practice/index.md.
.md
Markdown, a plain-text file format. Your notes, CLAUDE.md and NOTES.md are all .md files.
hidden file
A file whose name starts with a dot, such as .claude or .env. It is there, just not shown by default.
terminal
The text window where commands run. In the Code tab, Claude uses it for you and shows you what it ran.
command
One instruction to the computer, such as starting a program. Claude asks permission before each one.
script
A small program saved in a file, such as a check-up script that counts broken links.
local server
A small program on your own laptop that lets your browser open the pages in your folder.
localhost
The name your browser uses for "this computer." An address like http://localhost:8000 never leaves your laptop.
.env
A hidden file that holds secret keys for data sources. Claude reads keys from it so you never paste them into the chat.
API
Short for application programming interface. It is a door a website leaves open for programs instead of people, so code can ask it for data, such as a list of bills from Congress or a molecule from PubChem.
API key
A password-like code that a data source gives you so it knows who is asking. Keep it in your .env file, never in the chat.
MCP
Model Context Protocol, a standard way to plug new tools and data sources into Claude. Connectors use it.
subagent
A helper that Claude Code starts to handle one piece of a job. It works in its own conversation and reports back to the main session.
virtual environment
A folder that holds the Python software for one project, kept separate from the rest of your computer. Deleting the folder removes the software.
open model
An AI model whose weights anyone can download and run, often from Hugging Face. Small ones run on a laptop with tools like Ollama or LM Studio.
GLB
A common file format for 3D models with their colors and textures, used by web viewers and game engines.
STL
A file format for 3D shapes without color, used by 3D printers.
Gaussian splat
A way of storing a 3D scene as millions of soft, colored blobs instead of solid surfaces. It looks photographic, but there is nothing solid in it to bump into.
Monte Carlo simulation
Running the same calculation thousands of times with random inputs to see the range of possible results.
